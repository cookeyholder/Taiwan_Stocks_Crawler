## Context

本階段以前三階段完成的登入保護、API、行情頁、策略頁與持久化工作管理器為基礎。既有抓取邏輯在 `stock-core`，SQLite 僅有一個 VPS Web 寫入程序；沒有 Redis/worker 服務。

## Goals / Non-Goals

**Goals:** 透過網頁安全操作既有同步與補檔流程，顯示進度、取消與真實結果，讓長時間工作共用同一管理 API。

**Non-Goals:** 不建立多節點佇列、重試儀表板、即時推播或新的抓取算法；不改變核心來源限制。

## Decisions

- 由第三階段建立的 `stock-web` 工作管理器執行新增資料作業，狀態持久化於 SQLite；啟動時把上次程序留下的所有非終態工作標為中斷。
- 單日更新到日期區間補檔由服務端逐日呼叫可取消的 `Pipeline::fetch_date`；區間上限為五個日曆年且起訖日不得晚於臺北當日。於日期及每個上游 HTTP 請求邊界檢查取消，涵蓋 TWSE 備援請求、T86 與 TPEX；完成目前來源請求後、開始下一個來源請求前停止，回報每日期進度。
- BSR 僅接受臺北當日且建立時間不得早於 16:00；其餘日期或時間在建立工作前拒絕。
- 資料來源回應轉成 TWSE 行情、適用的 TWSE T86 法人資料及 TPEX 行情各自的 typed status，按所有子來源成功、有來源失敗但仍有資料、有效無資料、全數失敗分類；有效無資料不得自行推斷為休市，不可從 `message` 字串猜測。
- 所有長時間工作共用單一執行鎖，建立時若忙碌立即拒絕；工作完成/失敗/取消後才接受下一個長工作。一般短 API 查詢仍可使用。遵守現有 HttpClient retry/來源節流。
- 作業種類採明確列舉而非任意 shell command。所有參數經服務端驗證，呼叫 `stock-core` API，不經 shell 拼接。
- 作業進度 DTO 固定包含 `job_id`、狀態、階段、處理/總數、成功/失敗/略過數及可顯示訊息；錯誤細節寫入伺服器日誌，不回傳機敏資料。

## Risks / Trade-offs

- [程序重啟會中斷未完成工作] → 持久化工作狀態並於啟動時標記所有非終態工作中斷；行情匯入使用既有冪等 upsert/BSR 續傳重新執行。
- [批次任務佔用同一個程序] → 限制單一寫入批次、設定來源請求節流，並保留健康與查詢路由回應能力。
- [使用者誤以為部分失敗就是成功] → UI 明確顯示部分失敗和退出摘要，不只依 HTTP 接受請求顯示成功。

## Migration Plan

新增工作來源/結果分類欄位 migration，不變更行情資料格式。更新服務映像後可從網站啟動作業；回退只需回復舊映像，已寫入行情資料不需回滾，重啟中斷的作業可用既有冪等寫入再次執行。
